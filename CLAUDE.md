multirtmp — RTMP-релей с индивидуальной задержкой на каждый выход

Задача



vMix (Windows 11) публикует один RTMP-поток на 127.0.0.1. Программа принимает его, буферизует и раздаёт на несколько назначений, у каждого — своя задержка.



Практический сценарий: корпоративный сервер получает поток с нулевой задержкой, YouTube — с задержкой 10–15 с (точное значение подбирается на площадке).



Жёсткие правила



Нарушение любого из них — баг, а не компромисс.



Никакого перекодирования. Теги FLV перекладываются байт в байт. Никакого ffmpeg, никакого CGO, никаких кодеков в зависимостях.

Ingest-горутина ничего не делает, кроме копирования тега в буфер. Никакой записи в исходящие сокеты, никаких блокирующих мьютексов, удерживаемых выходами, никакого дискового I/O. Если YouTube встал — vMix не должен об этом узнать никак. Заблокированный ingest = закрытое TCP-окно = vMix обрывает публикацию.

Задержка не меняется на лету. Настроили в конфиге, запустили, работает. Изменение — только через явный рестарт выхода.

Один медленный выход не влияет на остальные. Каждый выход — своя горутина со своим курсором в общем буфере.

На всех исходящих записях обязателен SetWriteDeadline. Полумёртвый TCP в Windows может висеть в Write минутами.

Поддерживается ровно один активный источник. Второй publish с любым ключом вытесняет первый (см. раздел "Повторный publish") — несколько независимых потоков параллельно не поддерживаем.

Выход не открывает соединение с назначением, пока нет тега, готового к немедленной отправке с учётом задержки (Arrival + delay <= now) — не "тег есть в буфере", а именно "тег уже пора отправлять". Порядок строго: дождаться тега из буфера (курсор на keyframe, блокировка на sync.Cond, без сокета) -> дождаться Arrival+delay (тот же сон, что и у каждого следующего тега в пейсинге, только до connect, а не после) -> connect -> липкие теги -> цикл пейсинга. Простаивающее publish-соединение сервер назначения обрывает по своему read timeout (у MediaMTX 10с, у YouTube — аналогично): если открыть сокет раньше, чем тег реально готов к отправке, и потом просто держать соединение открытым до Arrival+delay, первая же запись упадёт с обрывом. Правило действует одинаково на первом подключении и на каждом реконнекте. Между connect и отправкой липких тегов должны проходить миллисекунды, а не секунды.

Тег

go

type Tag struct {

&#x20;   Kind    uint8      // 8 audio / 9 video / 18 data

&#x20;   TS      uint32     // абсолютный timestamp из RTMP

&#x20;   Arrival time.Time  // монотонное время приёма

&#x20;   Key     bool       // видео-keyframe

&#x20;   Data    \[]byte     // ОБЯЗАТЕЛЬНО копия payload

}



Data — именно копия: go-rtmp отдаёт буферы из пула и переиспользует их после возврата из колбэка.



Кольцевой буфер

Один на поток, общий; у каждого выхода свой курсор.

Размер считается в байтах, не в тегах. Ориентир: max\_delay \* bitrate \* 4.

Отдельно поддерживается список позиций keyframe'ов — нужен для старта и рестарта выходов.

Ожидание новых тегов — через sync.Cond, без busy-wait.

Липкие теги



Отдельно хранятся и обновляются при каждом приходе:



onMetaData

AVC sequence header (SPS/PPS)

AAC sequence header



Они отправляются первыми в каждое новое исходящее соединение, до первого кадра. Забыть про это — самая частая причина «поток идёт, картинки нет».



Логика выхода

подключиться -> отправить липкие теги -> встать на keyframe -> цикл:

&#x20;   взять тег из буфера

&#x20;   если delay > 0: спать до tag.Arrival + delay

&#x20;   записать с дедлайном

&#x20;   при ошибке -> reconnect



Пейсинг строго по Arrival, а не по внутренним timestamp'ам потока.



Выход с delay: 0 идёт по тому же коду, просто не спит. Отдельной ветки для него быть не должно.



Timestamp'ы

Каждое новое соединение — новый rebase от нуля: baseTS = TS первого отправленного тега, дальше TS - baseTS.

Учитывать extended timestamp: 24-битное поле переполняется через \~4,6 часа, обрабатывать и на чтении, и на записи.

Реконнект

Backoff: 0 → 0.5 → 1 → 2 → 5 с, дальше 5 с бесконечно.

Старт всегда с keyframe.

Выход с задержкой после обрыва продолжает с того места, где остановился (задержка временно вырастает, но контент не теряется). Если отставание превысило delay + 30s — прыгнуть вперёд на ближайший keyframe.

Выход с нулевой задержкой всегда прыгает на самый свежий keyframe.

Повторный publish



Новый publisher на тот же ключ вытесняет старый: буфер сбрасывается, выходы перезапускаются. Иначе после падения и рестарта vMix получим два конкурирующих источника.



Библиотеки

Приём: github.com/yutopp/go-rtmp (MIT)

Отдача: github.com/bluenviron/gortmplib (MIT) — тот же код, что раньше был в github.com/bluenviron/mediamtx pkg/protocols/rtmp, автор вынес его в отдельный публичный модуль (в текущих версиях mediamtx это стало internal/ и недоступно извне).

Архитектурное решение: gortmplib.Client используется ТОЛЬКО для handshake (connect/releaseStream/FCPublish/createStream/publish). Сам поток — все теги, включая AVC/AAC sequence header и onMetaData — пишется через pkg/rawmessage.Writer поверх того же net.Conn, байт в байт. Типизированный API (message.Video/Audio/DataAMF0) не использовать: он пересобирает sequence header через свою типизацию (mp4-box/AAC-конфиг) при каждой отправке и тем самым нарушает правило byte-in-byte.

Конвертация URL: снаружи принимаем привычный плоский вид rtmp://host/app/key (ключ потока — последний сегмент пути). gortmplib ждёт его в другом виде — rtmp://host/app#key (ключ во фрагменте). Конвертация — на границе перед созданием Client, внутренним кодом не протекает.



Обе MIT — исходники проекта закрытые, это допустимо.



Новые зависимости не добавлять без обсуждения. Стандартной библиотеки хватает для всего остального, включая HTTP API.

Окружение

Windows 11, Go 1.27, сборка и запуск нативно под Windows (не WSL).

Проект: C:\\multi-rtmp, модуль multirtmp.

MediaMTX: C:\\mediamtx\\mediamtx.exe — локальный приёмник для тестов.

ffmpeg/ffplay/ffprobe в PATH.



Сборка:



go build -o bin\\multirtmp.exe .\\cmd\\multirtmp



Релизная:



go build -ldflags="-s -w" -o bin\\multirtmp.exe .\\cmd\\multirtmp

Тестовый стенд

mediamtx.exe поднимает приёмник на 19350 (порт 1935 занят нашим ingest, 1936 занят другим сервисом).

vMix публикует на rtmp://127.0.0.1:1935/live/test.

Оба выхода идут на MediaMTX с разными ключами.

Два ffplay рядом; в кадре vMix — секундомер, разница между окнами должна равняться заданной задержке.



Проверка обрывов: погасить MediaMTX на 10 с и убедиться, что выход поднялся сам, а vMix при этом не заметил ничего.



План по этапам



Не делать следующий этап, пока предыдущий не проверен на реальном vMix.



&#x20;1. Приём. Только ingest, теги никуда не идут. В консоль: тегов/с, битрейт, fps, интервал keyframe'ов. Проверка — цифры совпадают с настройками vMix, 10+ минут без разрывов.

&#x20;2. Один выход, delay=0. Буфер + выход на MediaMTX. Проверка — ffplay показывает картинку и звук.

&#x20;3. Второй выход с задержкой. Проверка секундомером.

&#x20;4. Устойчивость. Реконнекты, backoff, watchdog на источник, дедлайны.

&#x20;5. Управление. config.json, HTTP API на 127.0.0.1, /status.

&#x20;6. Продакшн. Windows-служба, алерты, стрип бинарника, обкатка на площадке.

&#x20;7. Веб-интерфейс. Статика через embed, управление выходами (Add/Edit/Delete/Start/Stop с записью в config.json), доступ с планшета по LAN с токеном, опциональное превью через MediaMTX.

Правила работы с кодом

gofmt обязателен. go vet перед каждым коммитом.

Ошибки не глотать. Каждая — либо обработана, либо возвращена наверх с контекстом через fmt.Errorf("...: %w", err).

Никаких panic в ingest и в выходах. Recover на верхнем уровне каждой горутины с логированием.

Логи структурные, через log/slog. Уровни: ошибки соединений — Warn, потеря источника — Error, статистика — Debug.

Все пользовательские тексты — на английском: логи, тексты ошибок, алерты (Telegram), комментарии в config.json, будущий веб-интерфейс. Русского в выводе программы быть не должно вообще — ни в одном из этих мест. (Внутренние комментарии в самом коде и документация проекта — CLAUDE.md, PROGRESS.md — по-прежнему по-русски, это отдельное.)

Никаких «на всякий случай» абстракций и интерфейсов под один тип.

После каждого этапа обновлять PROGRESS.md: что сделано, что проверено, что дальше.

Что осознанно не делаем

Не поддерживаем HEVC/AV1 (enhanced RTMP) — только H.264 + AAC.

Не пишем на диск, не делаем запись трансляции.

Не делаем аутентификацию на ingest — слушаем только 127.0.0.1.

API по умолчанию — только 127.0.0.1, без токена. Доступ по LAN (с планшета) — только по явной настройке api.addr на не-loopback адрес, и тогда api.token обязателен: без него программа отказывается стартовать. Наружу в интернет API не открываем.
